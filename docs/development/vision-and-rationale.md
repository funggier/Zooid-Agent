# Vision and Rationale

## จุดเริ่มต้นและเหตุผลที่เปลี่ยนทาง

Zooid เริ่มจากความคิดใช้ Hermes เป็นฐานแล้วแยกตัวตน การติดตั้ง และระบบอัปเดต ต่อมาความต้องการชัดขึ้นว่าแกนการทำงานควรออกแบบตาม CogentNexus โดยตรง โดยเฉพาะการรักษาเจตนา งานระยะยาว การตรวจรับ และ lifecycle ที่สะอาด

การเปลี่ยนชื่อทั่วฐานโค้ดไม่ได้ทำให้ ownership ของงานและข้อมูลเปลี่ยนตาม จึงเลือกเริ่ม repository ใหม่และสร้างจากหน่วยเล็กสุด ผู้ใช้แจ้งว่าได้เปลี่ยนชื่อ repository เดิมแล้ว; ชื่อปลายทางของ repository เดิมไม่ได้ตรวจสอบในการจัดทำแผนนี้

ไฟล์ส่งต่อเดิม Pasted markdown(6).md อธิบายแนวทาง Hermes-derived และ coexistence เป็นประวัติของแนวคิด ส่วนข้อสรุปการสนทนาที่ตามมามีอำนาจเหนือแผนนั้น ไม่ยก independence audit เดิมมาเป็นงานแรกของโครงการใหม่

## เป้าหมาย

ทำให้ผู้ใช้เริ่มจากการคุยธรรมดาและค่อยพัฒนาเป็นงานที่มีเป้าหมาย ผู้ทำงาน ผู้ตรวจ และการประสานงาน โดยไม่สูญเสียที่มาหรือจำเป็นต้องเปิดบทสนทนาใหม่ทั้งหมด

ระบบควรทำงานต่อจาก checkpoint ได้แม้ session หรือ process เปลี่ยน และรู้ว่าต้องทำต่อ รอ ตรวจสอบ หรือหยุดด้วยเหตุผลใด ความสำเร็จต้องอ้างผลลัพธ์และหลักฐานตามประเภทงาน

คำว่า “ทำงานได้ตลอดเวลา” หมายถึงพร้อมรับเหตุการณ์และปลุกงานตามเงื่อนไขที่บันทึกไว้ ไม่ใช่เรียกโมเดลวนตลอดเวลา งานต้องมีขอบเขตทรัพยากร เงื่อนไขรอ และทางหยุดที่บังคับได้

## เหตุผลที่เริ่มเล็ก

| ทางเลือก | ข้อดี | ต้นทุน/เหตุผลตัดสิน |
| --- | --- | --- |
| เปลี่ยน fork เดิม | มีเครื่องมือจำนวนมากตั้งต้น | ต้องรับโครงสร้างและ lifecycle ที่ยังไม่ตรงเป้าหมาย |
| สร้างทุกระบบใหม่พร้อมกัน | ภาพปลายทางครบตั้งแต่แรก | ตรวจต้นเหตุยากและใช้เวลานานกว่าจะคุยได้ครั้งแรก |
| สร้างใหม่ทีละ slice | ทดสอบสมมติฐานได้เร็วและควบคุม ownership | ต้องรักษาสัญญาข้อมูลระหว่างขั้น; เป็นแนวทางที่เลือก |

ออกแบบขอบเขตให้ลึก แต่ให้ implementation โตตามความจำเป็น ทุก abstraction ควรมีผู้ใช้จริงและเกณฑ์ตรวจรับ ไม่สร้าง distributed framework ตั้งแต่ขั้นแรก

## ความสัมพันธ์กับ CogentNexus-OpenClaw

CogentNexus-OpenClaw เป็นทั้งแหล่งบทเรียนและเครื่องมือช่วยพัฒนา Zooid ในเครื่องผู้ใช้ เป้าหมายคือให้ผลลัพธ์พื้นฐานของ Zooid เทียบได้ก่อนขยายระดับ Project/Group โดยใช้ [baseline](acceptance/cogentnexus-baseline.md) ที่ผูกกับหลักฐานจาก revision จริง

Zooid ไม่จำเป็นต้องเรียก OpenClaw หรือ Hermes เพื่อรันแกนของตัวเอง การนำโค้ดหรือ skill จากภายนอกมาใช้ต้องตรวจ compatibility และบันทึกที่มาเป็นรายส่วน ไม่มีแผน sync upstream อัตโนมัติ

## หน่วยที่เติบโตและประกอบกันได้

ชื่อ Zooid สะท้อนหน่วยที่มีบทบาทเฉพาะและประกอบเป็นระบบร่วมกัน ส่วนอุปมาบริษัทช่วยอธิบาย Group เป็นองค์กร Project เป็นแผนก Session เป็นผู้ปฏิบัติงาน แต่ไม่ใช้เป็นลำดับชั้นตายตัว

แนวคิดที่ยึดจริงคือ Work Unit ที่มีตัวตนต่อเนื่องและเพิ่มความสามารถหรือเปลี่ยนความสัมพันธ์ได้ การยกระดับไม่ควรบังคับคัดลอกประวัติทั้งหมดหรือเพิ่มสิทธิ์โดยอัตโนมัติ

## สิ่งที่ใช้วัดความสำเร็จ

- คุยได้ง่ายและเปลี่ยน provider โดยรักษาประวัติที่รองรับได้
- งานไม่หายหรือถูกทำซ้ำอย่างไร้การควบคุมหลังความขัดข้อง
- งานยาวรักษาข้อกำหนดและเหตุผลตัดสินใจได้โดย context มีขอบเขต
- ผู้ใช้หยุด พัก ตรวจย้อนหลัง และเปลี่ยนโครงสร้างงานได้
- reset/uninstall/install-over/update มีผลชัดเจนและไม่เหลือ runtime เก่าทำงานซ้อน

รายได้ รูปแบบธุรกิจ และระบบกลุ่มบอทภายนอกยังไม่ใช่เป้าหมายของงานเริ่มต้น
